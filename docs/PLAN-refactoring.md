Otherwise sound: the YubiKey test holds the one worker slot, so no operation, reload or second test starts while it runs ([operation.go:62](../internal/gui/operation.go#L62), [reload.go:31](../internal/gui/reload.go#L31), [restoredialog.go:110](../internal/gui/restoredialog.go#L110)); the WebAuthn trace is written under a mutex and logs only lengths, never a credential ID, salt or secret ([webauthn.go:218](../internal/security/yubikey/webauthn.go#L218), [290](../internal/security/yubikey/webauthn.go#L290)), so Copy details keeps YK-9; `keycheck` zeroes the derived secret at once; the diagnosis only enumerates, opens each HID interface for a moment and reads the registry; a newer diagnosis request drops an older result; the device timer waits 500 ms for the burst of `DBT_DEVNODES_CHANGED`. Considered without an item: Yubico Authenticator is found through `%ProgramFiles%` before it is started elevated ([yubikey.go:187](../internal/gui/yubikey.go#L187)); a changed variable could point elsewhere, but only a process of the same user can change it, and Windows' elevation prompt names the program it starts.
- **Retention right after a backup, on a NAS whose flushes are not durable** (found 2026-10-24 by the MountSafe spike on the Mac mini share, MountSafe SPEC-core 14.5 item 7). The Mac's SMB server confirms `FlushFileBuffers` after about an `fsync` (0.70 ms over the network; `F_FULLFSYNC` on the Mac takes 3.07 ms), so the last writes it confirmed can be lost when the Mac loses power. A backup counts as complete when its last flush returns, and retention then deletes older backups in the same run (**Clean up**, GUI spec BR-2); a power loss shortly after can leave the new set damaged and the older ones already gone. `verify_after_backup` does not help: it may read back from the Mac's cache. To look at: run retention at the start of the next run, after the newest set has been checked again (`health`), or keep the previous complete set until the next run has checked the newest one. A change of when retention deletes is a behaviour change with a CHANGELOG entry; the format does not change. → RF-123 (decided 2026-10-25: `retention_keep` is at least 2).
- **The backup lock after a network drop** (same spike, MountSafe SPEC-core 6.6). A RestoreSafe run that ends while the NAS is unreachable (killed, crashed, PC switched off) leaves its open of the lock file on the Mac until the SMB durable timeout, about 3 minutes after the connection is back; until then the next backup, restore or verification reports the backup directory as locked. Measured on the Mac: a drop of a few seconds is hidden by Windows; after about a minute, handles kept open reattach; a handle closed during a drop leaves the orphan. To look at: whether `fsx/lock.go` and the workflows close handles on network errors (they should not), and whether the "locked" message can say that a lock left by this PC clears itself within minutes (as MountSafe SPEC-core 6.2 step 2 does). Looked at 2026-10-25: every workflow releases the lock with `defer lock.Release()` ([workflow.go:51](../internal/workflow/backup/workflow.go#L51), [restore/run.go](../internal/workflow/restore/run.go), [verify/workflow.go](../internal/workflow/verify/workflow.go)), so a run that ends with a network error closes the handle during the drop, which is exactly what leaves the orphan; and a failed lock says "Another RestoreSafe window is backing up, restoring or verifying" ([lock.go](../internal/fsx/lock.go)), which is wrong for an orphan. → RF-126.

### 5.1 From the specification review of 2026-10-24

## 12. Robustness and integrity (RF-123 to RF-127)

**RF-123 (P2) `retention_keep` is at least 2.** Evidence: retention deletes old chains at the end of the run that wrote the new sets ([workflow.go:261](../internal/workflow/backup/workflow.go#L261), core 9), once the new set's last flush has returned and it has been read back. - **The rule:** `retention_keep` is 0 (keep all) or at least 2; when retention runs and what it counts stay as today. `differential.retention_keep_differentials` keeps its minimum of 1: losing the newest differential leaves the chain's full backup.
- **A 1 in config.yaml** doesn't stop RestoreSafe, which would block restores too: Load uses 2 and records the adjustment (key, value in the file, value used, why). It shows as a warning (amber, warning triangle) with the code `CONFIG_ADJUSTED`, "A setting in config.yaml was changed for safety" (GUI spec 11.8): on Create backup as the hero with **Edit config**, as `ARGON2_CAPPED` does today; on Settings in the Retention card's row, with the warning glyph ("1 is used as 2. Set 2 or more in config.yaml."); and in the log of each backup. It goes away when the file says 2 or more and the configuration is reloaded.
- **One mechanism for adjusted settings:** the adjustment list of Load, the health warning and the row's warning are generic, so the KDF feature (SPEC-kdf 5.1, `ARGON2_BELOW_RECOMMENDED` and `ARGON2_OUT_OF_RANGE`) shows its values the same way instead of with a mechanism of its own.
- **`config-SAMPLE.yaml`**, the comment of `retention_keep`:
  ```yaml
  # 0 = keep all backups (no automatic cleanup). Any other value must be 2 or more:
  # RestoreSafe deletes old chains right after a new backup, and if the backup
  # disk or NAS loses power at that moment, the new backup can be damaged. The
  # second chain is then the backup you can still restore. A 1 is used as 2.
  ```
- Behaviour change: CHANGELOG entry; README (the `retention_keep` row); core 9 and the configuration section; GUI spec ST-6 and 11.8.

Acceptance: `config` tests: 0, 2 and 3 load unchanged, 1 loads as 2 with its adjustment, a negative value is still an error; a `health` test for `CONFIG_ADJUSTED`; `gui/view` tests of the hero and of the Retention row with its tone and glyph; with the retention code open anyway, a test per condition and rule of core 9 (section 5.1, round 2: "Check: retention preconditions and counting"). **Owner, before the release that ships it:** `retention_keep: 1` in a test configuration shows the warning on Create backup and Settings; after changing it to 2 and **Reload**, the warning is gone.

**RF-124 (P3) A TAR entry's offset and the bytes after end-of-archive are not checked.** Evidence: `ExtractSection` ([restore.go:100](../internal/format/archive/restore.go#L100)) checks each entry's type flag, name and size against the manifest, but not that its header starts at the entry's `off`, and `tar.Reader` stops at the end-of-archive marker without looking at what follows; core 7.4 and 7.5 make both a hard error, for full and differential restores. The data section is authenticated, so only someone with the keys can write such a stream; the check is defense in depth, and it makes the manifest's `off` binding, which a differential relies on, hold for every restore. Section 5.1, round 1.
Change: count the stream's position (a counting reader under `tar.Reader`), compare each header's position with `off`, and after end-of-archive accept only zero padding up to the end of the data section.
Acceptance: tests with a stream whose entry is shifted by one block and with data after end-of-archive, each refused with its cause; the 2.0.0 format fixtures still restore.

**RF-125 (P3) A lone surrogate in a typed secret changes or swallows a character.** Evidence: `ReadSecret` ([controls.go:108](../internal/gui/win32/controls.go#L108)) decodes a high surrogate together with the next unit whatever that is, so a high surrogate followed by `a` becomes U+FFFD and the `a` is gone; `\uD800a` and `\uD800b` give the same password. A lone surrogate at the end is encoded as itself, which is not valid UTF-8. Core 6.6 says lone surrogates are rejected. A keyboard doesn't type them, but a paste or an input method can. Section 5.1, round 3.
Change: `ReadSecret` reports a lone surrogate instead of converting it, and the credential dialog shows core 6.6's error under the field; nothing else of the conversion changes, so every valid password derives the same key as before.
Acceptance: `win32` tests for a lone high surrogate before a letter, at the end, and a lone low surrogate, each refused; the existing test that the conversion matches `string` conversion for valid input still passes.

**RF-126 (P2) A lock left on the NAS after a network drop.** Evidence: section 5. Every workflow releases the lock with `defer lock.Release()`, so a run that ends with a network error closes the handle during the drop, which leaves an orphaned open on the NAS for about 3 minutes (MountSafe SPEC-core 6.6, measured for share-mode opens); until then every backup, restore or verification of the directory, also from this PC, is refused with "Another RestoreSafe window is backing up, restoring or verifying", which is wrong for an orphan. Proposed 2026-10-25, decided the same day.
Change, after the measurement below:
- **Don't make the orphan.** The lock handle is never closed because of a network error. The window outlives a run, so a run that ends while the backup directory is unreachable hands its lock to the app; the app closes it when the directory answers again (the next check that reaches it), before it starts the next operation, or when it exits. Only a process that ends during the drop (killed, crash, power off) can still leave an orphan.
- **Recognise it and wait.** A backup, which holds the lock alone, writes a holder line into `restoresafe.lock` after the locked byte (computer, user, process ID, process start time, time); restores and verifications, which share the lock, write none. A run that can't get the lock reads the line. Another PC: "RestoreSafe on PC-OFFICE is backing up since 08:12." This PC, and the process is not a running RestoreSafe started before the time in the line (MountSafe SPEC-core 6.2 step 2's three-part test), or no line: the message says the lock is probably left by this PC after a lost connection and that the NAS releases it within a few minutes, and RestoreSafe tries again every 5 seconds for up to 5 minutes, with Cancel. "Another RestoreSafe window is …" stays for a RestoreSafe that runs on this PC.
- The lock file is kept on release (section 5.1, round 2). Behaviour change: CHANGELOG entry, core 14, the GUI's locked message.
Measurement first (owner, on the Mac share, with `tools/locktest`, 2026-10-25): whether the byte-range lock of `LockFileEx` reattaches after a drop of about a minute, how long the orphan of a handle closed during a drop lasts, the same for the shared lock, and whether a probe can read the holder line while the lock is held. The results go into this item and decide how much of the change is needed; a lock that reattaches and an orphan that lasts minutes need all of it.
Measured 2026-10-25 (owner, PC desktop-phs, share `\\10.10.10.10\Data_SSD` on the Mac, network cut by the owner, reachability logged every second; the probe tries every 5 s):
- **Kept open, the lock reattaches.** Exclusive, drop of 1 min 52 s: the handle failed 32 s after the cut ("The network path was not found."), worked again 6 s after the reconnect, and the probe found the lock held from then on until the holder closed it, released 1 s later. Shared, drop of 57 s: the same (works again after 5 s, held for 2 minutes, released 1 s after the close).
- **A handle closed during a drop leaves no orphan.** Exclusive, drops of 2 min 47 s and 54 s, closed 13 s and 3 s after the handle failed: the close returned at once without error, and the lock was free at the probe's first try after the reconnect (8 s and 6 s). Shared, drop of 60 s: free after 5 s. Unlike MountSafe's share-mode open (SPEC-core 6.6), a byte-range lock on an open with sharing is gone as soon as this PC's Windows reconnects: it either sends the close then or the Mac drops the lock; the drop's length doesn't matter.
- **A client that disappears leaves an orphan of about 2½ minutes.** Holder in Windows Sandbox (another SMB client), the Sandbox closed while holding the exclusive lock, this PC's network up: the probe found the lock held for 2 min 22 s after the close (14:56:32 to 14:58:54), with the holder line readable throughout. This is the case of a PC switched off or crashed during a run; nothing is left to send the close.
- **The holder line is readable while the lock is held**, by this PC and while orphaned; without a drop a closed lock is free within the probe's 5 s.
Decided by the owner 2026-10-25: **"Don't make the orphan" is dropped** (a run that ends with a network error releases the lock correctly; this PC's reconnect frees it); **"Recognise it and wait" is kept**, for a PC that was switched off or crashed, which on restart is refused for about 2½ minutes with the wrong message; 5 minutes of retries cover it. The orphan of a PC that disappears is the same for another PC, so the message for another PC adds that the lock is released within a few minutes if that PC was switched off or lost its connection; it doesn't wait, since only that PC's owner knows whether it still runs. Without a holder line, the lock counts as held by a RestoreSafe of this PC when another RestoreSafe process runs here ("Another RestoreSafe window is …" stays), otherwise as left behind. The backup empties the file on release, so that a line never outlives its backup.
Follow-up, decided by the owner 2026-10-25: only the Mac was measured, and another server may keep the lock of a handle closed during a drop, as MountSafe's share-mode open showed. Then a run that ends with a network error leaves its lock, and the next run in the same window, whose process still runs, was refused with "Another RestoreSafe window is …" without waiting. A holder line that names the process itself now counts as left behind: the window runs one operation at a time and holds no lock when it starts one.
Acceptance: tests with a fake lock file system (a holder line of this PC with a process that isn't running, of another PC, of this process, none) for the message and the retry; the three-part test against this process; the scenario of the Sandbox repeated with RestoreSafe itself on the Mac share (owner): a backup in the Sandbox, the Sandbox closed, a backup on the PC waits and starts once the NAS releases the lock.
